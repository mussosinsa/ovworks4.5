## 2. 목적 및 적용 범위

본 확인서는 조직 내부의 사설 인증기관(Private CA)이 발급하는 SSL/TLS 서버 인증서를 안전하게 발급·배포·갱신·폐기하는 정책과 검증 절차를 정의한다. 공개 CA 인증서나 Engine 내부 구성요소 간 인증서는 해당 인증서의 별도 수명주기 정책을 우선 적용한다.

보안 목표는 다음과 같다.

1. 서버 신원과 인증서 요청 주체를 검증한다.
2. 개인키의 기밀성과 무결성을 수명주기 전체에서 보호한다.
3. 인증서 만료 전에 계획적으로 갱신하여 서비스 중단을 예방한다.
4. 취약한 프로토콜·암호군 및 잘못된 인증서 체인을 차단한다.
5. 신청, 승인, 발급, 배포, 검증, 폐기 활동의 추적 가능한 증적을 남긴다.

### 2.1 관리 대상

| 구분 | 관리 항목 | 기준 |
|---|---|---|
| 서버 인증서 | HTTPS 종단점 인증서와 중간 CA 체인 | FQDN을 SAN에 포함, 서버 인증 용도 확인 |
| 개인키 | 서버 인증서와 쌍을 이루는 비밀키 | 대상 서버에서 생성, 평문 외부 반출 금지 |
| 신뢰 체인 | Root CA 및 Intermediate CA 인증서 | 사전 승인된 신뢰 저장소에만 배포 |
| 폐기 정보 | CRL 또는 OCSP 정보 | 조직 PKI 정책에 따라 게시·점검 |
| 설정 | Apache HTTP Server 및 연계 서비스의 TLS 설정 | TLS 1.2 이상, 승인 암호군 사용 |

## 4. 인증서 갱신 주기

### 4.1 표준 정책

인증서의 실제 `notAfter`를 단일 기준으로 삼으며, 다음 주기는 조직의 PKI 정책 또는 인증서 프로파일이 더 짧은 기간을 요구하면 그 값을 우선한다.

| 대상 | 최대 유효기간 | 정기 갱신 착수 | 발급·배포 완료 목표 | 비고 |
|---|:---:|:---:|:---:|---|
| 운영 서버 인증서 | 397일 이내 | 만료 60일 전 | 만료 30일 전 | 연 1회 이상 교체 |
| 개발·시험 서버 인증서 | 397일 이내 | 만료 30일 전 | 만료 14일 전 | 운영 인증서·키 재사용 금지 |
| Root/Intermediate CA | 조직 PKI 정책에 따름 | 만료 1년 전 영향 분석 | 하위 인증서 만료보다 충분히 이전 | 서버 인증서 절차와 분리 |

397일은 본 시스템의 **내부 보안 운영 상한**이며 사설 인증서에 대한 법정 유효기간을 의미하지 않는다. 자동화와 단기 인증서 프로파일을 운영할 수 있으면 90일 이하를 권장한다. 갱신 시에는 원칙적으로 새 개인키를 생성하며 동일 키 재사용은 보안 책임자의 서면 승인이 있는 예외로 제한한다.

### 4.2 수시 갱신·긴급 재발급 조건

다음 상황은 잔여 유효기간과 관계없이 즉시 변경 티켓을 생성하고 신규 키로 재발급한다.

- 개인키 유출 또는 유출 의심, 비인가 접근, 파일 무결성 훼손
- 인증서의 FQDN/SAN, 조직 정보 또는 용도가 실제 서비스와 불일치
- 호스트명·도메인·서비스 소유자 변경 또는 서버 폐기
- 서명 알고리즘이나 키 길이가 조직 기준 미달 또는 취약 판정
- CA 침해, 인증서 오발급, 신뢰 체인 변경 또는 폐기 요청

## 5. 역할과 책임

| 역할 | 책임 | 금지 사항 |
|---|---|---|
| 서비스 소유자 | 대상 FQDN·SAN·점검 시간 확인, 발급 신청 | 승인 없이 운영 반영 |
| PKI 담당자 | 신청 정보 검증, 인증서 발급·폐기, CRL/OCSP 운영 | 서버 개인키 수령·보관 |
| 변경 승인자 | 영향도, 작업·롤백 계획, 작업 창 승인 | 본인이 신청한 변경의 단독 승인 |
| 시스템 운영자 | 키·CSR 생성, 백업, 배포, 서비스 재로딩 | 개인키를 티켓·메일에 첨부 |
| 보안 검증자 | 체인·SAN·TLS·로그 독립 확인, 최종 판정 | 검증 전 완료 처리 |

## 6. 신규 발급 절차

### 6.1 신청 및 사전 확인

1. 자산번호, 서비스명, 운영/비운영 구분, FQDN과 모든 SAN, 소유자, 발급 프로파일 및 적용 일정을 변경 티켓에 기록한다.
2. DNS 소유권과 신청자의 서버 관리 권한을 확인한다.
3. 와일드카드 인증서는 필요성을 별도 승인받고 사용 범위를 최소화한다. IP 주소는 실제 접속에 필요한 경우에만 SAN에 포함한다.
4. 승인된 알고리즘, 키 길이, 서명 알고리즘 및 인증서 용도(`serverAuth`)를 확인한다.

### 6.2 개인키와 CSR 생성

대상 Engine 서버의 제한된 작업 디렉터리에서 실행한다. 다음은 RSA 예시이며 실제 값은 조직 PKI 프로파일을 따른다.

```bash
install -d -m 0700 /root/tls-work
openssl genpkey -algorithm RSA \
  -pkeyopt rsa_keygen_bits:3072 \
  -out /root/tls-work/engine.example.internal.key
chmod 0600 /root/tls-work/engine.example.internal.key

openssl req -new -sha256 \
  -key /root/tls-work/engine.example.internal.key \
  -out /root/tls-work/engine.example.internal.csr \
  -subj "/O=Example/CN=engine.example.internal" \
  -addext "subjectAltName=DNS:engine.example.internal"
```

CSR의 서명, 공개키 정보와 SAN을 확인한 후 **CSR만** PKI 담당자에게 전달한다.

```bash
openssl req -in /root/tls-work/engine.example.internal.csr \
  -noout -verify -subject -text
```

### 6.3 승인 및 발급

1. PKI 담당자는 티켓 승인, 신청자 권한, CN/SAN, 키 규격 및 중복 발급 여부를 확인한다.
2. 승인된 서버 인증서 프로파일로 CSR에 서명한다.
3. 서버 인증서, Intermediate CA 체인, Root CA, 일련번호, 유효기간 및 SHA-256 지문을 반환한다. 개인키는 반환물에 포함하지 않는다.
4. 발급 기록에 신청·승인자, 발급 시각, 프로파일, 일련번호, 만료일과 티켓 번호를 기록한다.

### 6.4 반영 전 검증

```bash
# 인증서 내용과 서버 인증 용도 확인
openssl x509 -in server.crt -noout \
  -subject -issuer -serial -dates -fingerprint -sha256 -ext subjectAltName

# 개인키와 인증서의 공개키 일치 여부 확인
test "$(openssl pkey -in /root/tls-work/engine.example.internal.key -pubout -outform DER | sha256sum)" = \
     "$(openssl x509 -in server.crt -pubkey -noout | openssl pkey -pubin -outform DER | sha256sum)"

# 사설 CA 체인 확인
openssl verify -purpose sslserver \
  -CAfile root-ca.crt -untrusted intermediate-ca-chain.crt server.crt
```

모든 검증이 성공해야 배포를 승인한다. Root CA는 클라이언트의 승인된 신뢰 저장소에 별도로 배포하며, 서버가 전송하는 체인 파일에는 일반적으로 서버 인증서와 필요한 Intermediate CA만 구성한다.

## 7. 정기 갱신 절차

### 7.1 준비

1. 만료 60일 전 모니터링 알림으로 갱신 티켓을 자동 또는 수동 생성한다.
2. 현재 인증서의 SAN, 사용 위치, 의존 서비스와 클라이언트 신뢰 배포 현황을 조사한다.
3. 변경 승인, 작업 창, 서비스 영향, 담당자와 롤백 기준을 확정한다.
4. 현재 인증서·체인·개인키·TLS 설정을 접근 제한된 백업 위치에 보관하고 파일 해시를 기록한다.
5. 6장의 절차로 **새 개인키와 CSR**을 생성하여 발급받고 스테이징 환경 또는 별도 포트에서 검증한다.

### 7.2 배포

1. 실제 Apache 설정에서 인증서·개인키·체인 경로를 확인한다. 경로를 추정하여 덮어쓰지 않는다.
2. 신규 파일을 임시 이름으로 복사하고 소유자, 그룹, 권한과 SELinux 컨텍스트를 기존 정책에 맞춘다.
3. 원자적 파일 교체 또는 버전 디렉터리와 심볼릭 링크 전환 방식으로 반영한다.
4. 설정 문법 검사에 성공한 뒤 승인된 작업 창에 HTTP/TLS 서비스를 reload 또는 restart한다.

```bash
# 실제 배포 경로로 치환한다.
apachectl configtest
systemctl reload httpd
systemctl --no-pager --full status httpd
```

WebSocket proxy, ImageIO 등 별도 인증서 경로를 사용하는 연계 서비스가 있으면 각 서비스 설정을 확인하고 동일한 승인·검증 절차로 반영한다. `engine-setup`을 이용하는 방식은 제품 버전과 설치 형태에 따라 동작이 달라질 수 있으므로 사전 백업과 시험 환경 검증 후 수행한다.

### 7.3 사후 검증

```bash
# SNI를 포함하여 실제 서비스가 제공하는 인증서와 체인을 확인
openssl s_client -connect engine.example.internal:443 \
  -servername engine.example.internal -showcerts -verify_return_error </dev/null

# 호스트명, 체인과 HTTPS 응답 확인(사설 CA 지정)
curl --fail --silent --show-error \
  --cacert root-ca.crt https://engine.example.internal/ >/dev/null

# 허용 프로토콜 확인
openssl s_client -connect engine.example.internal:443 \
  -servername engine.example.internal -tls1_2 </dev/null
```

다음 항목을 모두 확인한다.

- 외부에서 조회한 일련번호·SHA-256 지문이 신규 인증서와 일치한다.
- FQDN과 SAN이 일치하고 체인이 승인된 사설 Root CA까지 검증된다.
- 인증서 유효기간, `serverAuth`, 서명 알고리즘과 키 길이가 정책에 적합하다.
- TLS 1.2 이상으로 연결되며 SSLv2/3, TLS 1.0/1.1은 허용되지 않는다.
- WebAdmin, VM Portal, REST API 로그인과 주요 연계 기능이 정상 동작한다.
- Apache 및 Engine 로그에 TLS, 키 접근 권한 또는 체인 오류가 없다.

검증자가 결과를 티켓에 첨부하고 서비스 소유자가 정상 동작을 확인한 뒤 작업을 완료한다. 구 인증서와 키는 롤백 기간 종료 후 보존 정책에 따라 안전하게 삭제하며, 재사용하지 않는다.

## 8. 실패 시 롤백 및 긴급 대응

### 8.1 롤백 기준과 절차

체인 오류, 키 불일치, 서비스 기동 실패, 주요 클라이언트 접속 실패 또는 예상하지 못한 인증 오류가 발생하면 즉시 롤백한다.

1. 신규 반영을 중단하고 변경 책임자 및 보안 담당자에게 통보한다.
2. 백업한 구 인증서·키·체인과 설정을 원래 권한으로 복원한다.
3. `apachectl configtest` 후 서비스를 reload/restart한다.
4. HTTPS와 주요 업무 기능의 복구를 확인한다.
5. 장애 시간, 원인, 복원 시각과 검증 결과를 사고·변경 티켓에 기록한다.

### 8.2 개인키 침해 대응

1. 의심 키의 사용을 중지하되 서비스 가용성을 고려하여 긴급 교체 절차를 개시한다.
2. PKI 담당자에게 해당 인증서 폐기를 요청하고 CRL/OCSP 반영을 확인한다.
3. 기존 키와 무관한 새 개인키로 CSR을 생성하여 긴급 재발급한다.
4. 신규 인증서 배포 후 모든 종단점과 연계 시스템을 점검한다.
5. 접근 로그와 변경 이력을 보존하고 사고 대응 절차에 따라 영향 범위와 유출 원인을 조사한다.

## 9. 모니터링 및 감사기록

### 9.1 만료 모니터링

- 일 1회 이상 모든 관리 대상 종단점을 SNI 방식으로 조회한다.
- 잔여 60일은 운영 담당자, 30일은 서비스 소유자·보안 담당자, 14일은 부서 책임자, 7일은 긴급 대응 체계에 통보한다.
- 인증서 조회 실패, 체인 오류, SAN 불일치 또는 7일 미만 잔여기간은 장애 경보로 처리한다.
- 자산대장에는 FQDN, 포트, 인증서 일련번호, 지문, 발급자, 만료일, 담당자 및 갱신 티켓을 기록한다.

### 9.2 감사 증적과 보존

| 증적 | 필수 내용 | 보존 기준 |
|---|---|---|
| 발급·갱신 티켓 | 신청·승인자, FQDN/SAN, 사유, 일정, 결과 | 조직 보존 정책 또는 최소 3년 중 더 긴 기간 |
| 인증서 메타데이터 | 일련번호, 발급자, 유효기간, SHA-256 지문 | 인증서 폐기 후에도 감사 기간 동안 보존 |
| 작업 기록 | 명령 결과, 파일 권한, 서비스 상태, 작업자·시각 | 개인키·비밀번호를 제거하여 보관 |
| 시험 결과 | 체인, 호스트명, TLS 버전, 기능시험, 판정 | 변경 티켓과 연계 |
| 폐기 기록 | 폐기 사유, 요청·승인·반영 시각, CRL/OCSP 확인 | 사고 기록과 연계 |

## 10. 제출용 점검표 및 결재

### 10.1 점검표

- [ ] 관리 대상 FQDN, 포트, SAN 및 인증서 사용 위치를 자산대장과 대조하였다.
- [ ] 운영 인증서 유효기간은 397일 이내이며 만료 60일 전 갱신 절차를 시작한다.
- [ ] 개인키는 서버에서 생성되었고 최소 권한 및 접근통제가 적용되었다.
- [ ] CSR 정보, 인증서 용도, SAN, 체인, 공개키 일치 및 지문을 확인하였다.
- [ ] 변경 승인, 백업, 배포, 롤백 계획과 작업자 분리가 확인되었다.
- [ ] 실제 외부 접속으로 신규 인증서, 체인, 호스트명 및 TLS 1.2 이상을 확인하였다.
- [ ] WebAdmin, VM Portal, REST API 및 연계 서비스의 정상 동작을 확인하였다.
- [ ] 만료 알림과 긴급 폐기·재발급 연락 체계가 동작한다.
- [ ] 증적에서 개인키, PIN 및 비밀번호를 제거하고 승인된 저장소에 보관하였다.
