## 2. 목적 및 범위

본 확인서는 Engine 데이터베이스 접속정보가 저장되는 `10-setup-database.conf`의 기밀성·무결성을 보호하기 위한 저장 암호화 방법, 암호 알고리즘 기준, 키 관리, 적용·복구 절차와 시험 방법을 정의한다.

대상 파일에는 다음과 같은 정보가 포함될 수 있다.

| 구분 | 예시 키 | 보안 분류 | 보호 방법 |
|---|---|---|---|
| 인증정보 | `ENGINE_DB_PASSWORD` | 비밀(Secret) | 파일 전체 암호화, 키 분리 보관 |
| 계정정보 | `ENGINE_DB_USER` | 중요정보 | 파일 전체 암호화, 최소 권한 |
| 접속정보 | `ENGINE_DB_HOST`, `ENGINE_DB_PORT`, `ENGINE_DB_DATABASE` | 내부정보 | 파일 전체 암호화, 접근통제 |
| TLS 설정 | `ENGINE_DB_SECURED`, `ENGINE_DB_SECURED_VALIDATION` | 보안 설정 | 무결성 보호 및 변경 감사 |

본 문서에서 말하는 **저장 암호화**는 파일시스템에 저장된 설정 파일을 보호하는 통제이다. PostgreSQL 전송 구간 TLS, 데이터베이스 자체 암호화, 디스크 암호화 및 백업 암호화는 별도의 통제이며 서로 대체하지 않는다.

## 3. 제품 연동 구조 확인

제품은 다음 경로의 암·복호화 도구와 설정을 사용하도록 연동되어 있다.

| 구성요소 | 기본 경로 | 용도 |
|---|---|---|
| 암·복호화 도구 | `/usr/share/ovirt-engine/encryptor/encryptor.py` | 승인된 설정 파일 암호화·복호화 |
| 암호화 설정 | `/etc/ovirt-engine/encryptor/config.json` | 암호 파라미터 및 도구 동작 설정 |
| 키 파일 | `/etc/ovirt-engine/encryptor/private_pkcs8.der` | 복호화에 사용하는 PKCS#8 개인키(설치 구성에 따라 존재) |
| 대상 설정 | `/etc/ovirt-engine/engine.conf.d/10-setup-database.conf` | Engine DB 접속 설정 |

`engine-setup`의 DB 연결 단계는 허용 목록에 포함된 `10-setup-database.conf`에 대해서만 도구의 `--decrypt` 또는 `-d` 모드를 호출하고, 복호화 결과에 `ENGINE_DB_PASSWORD`가 없으면 원본을 복원한다. `engine-backup`도 허용된 파일만 복호화하며 작업 후 암호문 원본을 복원한다. 따라서 임의 파일 복호화 방지와 실패 시 원본 보존 기능을 확인 대상으로 삼는다.

> **중요:** 저장소의 `packaging/encryptor/encryptor.py`는 `OVENC001` 버전 1, AES-256-GCM 및 PBKDF2-HMAC-SHA-256 600,000회를 구현한다. 제출 환경에서도 설치 파일의 버전·해시가 이 소스와 일치하는지 확인해야 한다.

## 4. 암호화 방식 및 알고리즘

### 4.1 승인 암호 프로파일

신규 구축 또는 암호 모듈 변경 시 다음 이상의 프로파일을 적용한다.

| 기능 | 승인 기준 | 금지 또는 부적합 기준 |
|---|---|---|
| 파일 본문 암호화 | **AES-256-GCM** 등 256비트 키의 인증된 암호(AEAD) | ECB, DES, 3DES, RC4, 무결성 없는 CBC/CTR 단독 사용 |
| Nonce/IV | CSPRNG으로 매 암호화마다 새 값 생성, AES-GCM은 통상 96비트 | 고정값 또는 동일 키에서 재사용 |
| 인증 태그 | 128비트 권장, 최소 96비트 | 태그 미검증 또는 96비트 미만 |
| 키 래핑 | PBKDF2 유도 256비트 KEK를 사용하는 **AES-256-GCM** | 인증되지 않은 래핑, 키 평문 저장 |
| 비밀번호 기반 키 유도 | PBKDF2-HMAC-SHA-256 600,000회, 무작위 128비트 salt | 고정 salt, SHA-1 단독, 단순 해시 |
| 난수 생성 | OS CSPRNG(`/dev/urandom`, 검증된 암호 라이브러리) | 시간·일련번호 기반 의사 난수 |
| 무결성 | AEAD 태그 검증 실패 시 평문 출력 및 원본 변경 금지 | 오류를 무시한 복호화 |

파일마다 무작위 데이터 암호화 키(DEK)를 생성해 본문을 암호화하고, DEK는 PBKDF2로 유도한 키 암호화 키(KEK)를 이용해 별도 AES-GCM nonce와 태그로 래핑한다. passphrase 또는 KEK는 암호문과 분리하고 파일에 직접 삽입하지 않는다.

### 4.2 실제 적용 알고리즘 확인표

다음 값은 운영 서버의 설치 도구 또는 공급자 명세에서 확인하여 기입한다. 승인 기준과 다르면 `부적합`으로 판정하고 암호 모듈을 교체한다.

| 확인 항목 | 운영 적용값 | 확인 방법 | 판정 |
|---|---|---|:---:|
| 파일 암호 알고리즘 / 키 길이 | AES-256-GCM / 256비트 DEK | 소스·암호문 형식 확인 | `[ ]` |
| Nonce/IV 길이 및 생성 방식 | 96비트 / OS CSPRNG | 구현 및 반복 암호화 결과 비교 | `[ ]` |
| 인증 태그 길이 | 128비트 | 구현 및 변조 시험 | `[ ]` |
| 키 래핑 알고리즘 | AES-256-GCM | 구현 확인 | `[ ]` |
| 키 공급 | systemd credential 기본, 환경변수·0600 비밀 파일 지원 | 실행 환경·권한 확인 | `[ ]` |
| KDF / 반복 횟수 / salt 길이 | PBKDF2-HMAC-SHA-256 / 600,000 / 128비트 | 헤더와 구현 확인 | `[ ]` |
| 암호 모듈 버전 / SHA-256 | `[ ] / [ ]` | 패키지 정보 및 `sha256sum` | `[ ]` |

암호화 설정에 `iterations`, `salt`, `nonce` 등이 있더라도 구현에서 실제로 사용되는지 확인한다. `decrypt_key`처럼 복호화 가능한 평문 키가 설정 파일에 존재하면 키 분리 원칙 위반으로 판정하고 제거·재발급한다. 제출 증적에는 해당 값 자체가 아니라 존재 여부, 길이 및 마스킹된 해시만 기록한다.

## 6. 최초 암호화 적용 절차

### 6.1 사전 준비

1. 변경 티켓에 대상 호스트, 파일, 암호 모듈 버전, 작업자, 승인자, 작업 시간 및 롤백 계획을 기록한다.
2. Engine과 DB 접속 상태를 확인하고 승인된 보안 저장소에 현재 설정을 백업한다.
3. 설치된 도구가 제공하는 정확한 암호화 옵션과 알고리즘을 확인한다.

```bash
sudo /usr/bin/python3 /usr/share/ovirt-engine/encryptor/encryptor.py --help
sudo rpm -qf /usr/share/ovirt-engine/encryptor/encryptor.py
sudo sha256sum /usr/share/ovirt-engine/encryptor/encryptor.py
```

4. 파일과 키의 실제 소유자·권한·SELinux 컨텍스트를 증적으로 남긴다. 값이 노출되는 `cat`, `grep ENGINE_DB_PASSWORD` 결과는 수집하지 않는다.

```bash
sudo stat -c '%n %U:%G %a %s bytes' \
  /etc/ovirt-engine/engine.conf.d/10-setup-database.conf \
  /etc/ovirt-engine/encryptor/config.json
sudo ls -lZ /etc/ovirt-engine/engine.conf.d/10-setup-database.conf \
  /etc/ovirt-engine/encryptor/config.json
```

### 6.2 암호화 실행

1. 서비스 계정이 읽을 수 있는 암호문 파일을 임시 경로에 생성한다. 비밀번호를 명령행 인자로 전달하지 않는다.
2. **운영 서버에서 확인한 `--help`의 암호화 옵션만 사용한다.** 제품 버전별 CLI가 다를 수 있으므로 본 문서는 검증되지 않은 옵션을 고정하지 않는다.
3. 출력 파일의 소유자·그룹·권한을 기존 서비스 정책과 동일하게 설정하고 `restorecon`을 적용한다.
4. 원본과 같은 디렉터리에서 원자적 `rename`으로 교체한다. 성공 전 평문 원본을 삭제하지 않는다.
5. 7장의 시험에 성공한 후 접근 제한된 평문 백업과 임시파일을 안전하게 폐기한다.

권장 권한 기준은 암호화 설정 디렉터리 `0700`, 개인키 `0600`, 데이터베이스 설정 파일은 서비스 실행에 필요한 최소 읽기 권한이다. 실제 소유자는 패키지·서비스 정책을 우선하며 임의로 변경하지 않는다.

### 6.3 서비스 반영

```bash
sudo restorecon -Rv /etc/ovirt-engine/encryptor \
  /etc/ovirt-engine/engine.conf.d/10-setup-database.conf
sudo systemctl restart ovirt-engine
sudo systemctl --no-pager --full status ovirt-engine
```

재기동 후 Engine의 DB 연결, WebAdmin 로그인, REST API 조회 및 로그 오류 여부를 확인한다. 암호화 도구가 상주 프로세스 또는 사전 복호화 단계에 의존하는 설치 형태라면 해당 서비스의 기동 순서와 실패 정책도 함께 증적화한다.

## 7. 자체 시험 절차

시험은 운영 비밀번호가 아닌 시험 계정과 파일 사본으로 수행한다.

### 7.1 암·복호화 및 비결정성 시험

1. 동일한 시험 평문을 서로 다른 출력 파일로 두 번 암호화한다.
2. 두 암호문의 SHA-256이 달라 nonce/IV가 매번 갱신되는지 확인한다.
3. 두 파일을 복호화하여 원문 SHA-256과 일치하는지 확인한다.
4. 명령 출력, 작업 디렉터리, 셸 이력과 로그에 비밀번호가 남지 않았는지 확인한다.

### 7.2 무결성·오류 처리 시험

1. 암호문 사본의 본문 1바이트를 변경한다.
2. 복호화를 실행하여 비정상 종료되는지 확인한다.
3. 평문이 출력되지 않고 암호문 원본이 변경·삭제되지 않는지 확인한다.
4. 잘못된 키, 누락된 키, 잘못된 권한 및 손상된 `config.json` 조건도 같은 방식으로 확인한다.

### 7.3 운영 연동 시험

```bash
# 비밀값 없이 프로세스·서비스 상태 확인
sudo systemctl is-active ovirt-engine
sudo journalctl -u ovirt-engine --since '[시험 시작 시각]' \
  | sed -E 's/(PASSWORD|password)([^ ]*)/\1=[REDACTED]/g'

# 설정/백업 도구의 암호문 처리 성공 여부 확인
sudo engine-setup --offline
sudo engine-backup --mode=backup \
  --file=/var/lib/ovirt-engine/backups/encrypted-config-test.bck \
  --log=/var/log/ovirt-engine/encrypted-config-test.log
```

`engine-setup --offline`은 실제 설정 변경 가능성이 있으므로 승인된 시험 환경 또는 변경 작업 창에서만 수행한다. 시험 완료 후 대상 파일이 다시 암호문 상태인지 확인하며, 로그 수집 전 정규식뿐 아니라 담당자가 비밀정보 포함 여부를 재검토한다.

## 8. 키 관리 및 교체

| 항목 | 운영 기준 |
|---|---|
| 생성 | OS CSPRNG 또는 HSM/KMS에서 생성하고 작업자 개인 키를 사용하지 않는다. |
| 보관 | 암호문과 다른 보안 경계에 두며 `root`/전용 서비스 계정만 접근한다. |
| 백업 | 암호문과 키를 서로 다른 접근권한의 저장소에 암호화하여 백업한다. |
| 교체 주기 | 연 1회 위험 검토, 최대 2년마다 KEK/개인키 교체를 권장한다. 조직 정책이 더 짧으면 이를 따른다. |
| 즉시 교체 | 키 유출 의심, 퇴직·권한변경, 알고리즘 취약화, 키 파일 무결성 훼손 시 즉시 수행한다. |
| 폐기 | 신규 키로 재암호화 및 복구 시험 후 구 키를 승인 절차로 폐기한다. |

키 교체 시 새 키 쌍으로 설정 파일을 재암호화하고, 모든 Engine·DWH·백업 연계가 새 키로 동작하는지 확인한다. 구 키는 정해진 롤백 기간 동안 오프라인 보관한 뒤 복구 불가능한 방식으로 폐기한다.

## 9. 장애 복구 및 롤백

다음 중 하나가 발생하면 변경을 중단한다: 복호화 실패, 인증 태그 오류, DB 연결 실패, Engine 기동 실패, 키 접근 거부, 암호문이 평문으로 남는 현상.

1. 대상 서비스와 자동 암·복호화 작업을 중지하고 보안·운영 책임자에게 통보한다.
2. 실패 파일과 로그의 무결성 해시를 보존하되 비밀값은 마스킹한다.
3. 승인된 백업에서 직전 암호문과 해당 키를 원래 권한·컨텍스트로 복원한다.
4. 서비스 정상화 및 DB 연결을 확인한다.
5. 평문 임시파일, core dump, swap, 작업 로그와 백업 부산물의 노출 여부를 조사한다.
6. 원인과 조치 결과를 기록하고 재시험 승인 전 재적용하지 않는다.

개인키 유출이 의심되면 단순 파일 복원으로 종결하지 않고 신규 키 생성, 전체 대상 재암호화, 구 키 폐기 및 접근 이력 조사를 수행한다.

## 10. 운영 점검 및 증적

### 10.1 정기 점검

- **일 1회:** 대상 파일이 암호문 상태인지, 권한·소유자·서비스 상태가 정상인지 점검한다.
- **월 1회:** 암호 모듈·키 파일 무결성, 실패 로그, 비인가 접근 및 평문 부산물을 점검한다.
- **분기 1회:** 복호화 실패·변조 탐지 및 백업 복구 모의시험을 수행한다.
- **연 1회:** 알고리즘 안전성, 키 크기, 키 교체 필요성 및 공급자 보안 업데이트를 검토한다.

### 10.2 제출용 체크리스트

- [ ] `ENGINE_DB_PASSWORD`가 저장 매체에 평문으로 존재하지 않는다.
- [ ] 실제 암호 알고리즘·키 길이·nonce·태그·KDF를 구현 또는 공급자 명세로 확인했다.
- [ ] 설정 파일과 키 파일의 소유자·권한·SELinux 컨텍스트가 최소 권한이다.
- [ ] 동일 평문 반복 암호화 결과가 다르고 모두 정상 복호화된다.
- [ ] 암호문 변조 시 복호화가 실패하며 평문이나 부분 결과를 출력하지 않는다.
- [ ] `engine-setup`, `engine-backup` 및 Engine 재기동 후 암호문이 복원·유지된다.
- [ ] 로그, 셸 이력, 프로세스 인자, 임시파일과 백업에 평문 비밀번호가 없다.
- [ ] 키와 암호문이 분리 백업되며 복구 시험에 성공했다.
- [ ] 키 교체·유출 대응·롤백 절차와 담당자가 지정되어 있다.
